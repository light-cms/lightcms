Документація - це частина проекту, з яким кожен погоджується має значення, і ніхто не погоджується щодо того, як впоратися. Подивіться на 5 відкритих проектів, і ви знайдете 5 різних налаштувань. Деякі добре працюють. Багато з них пливли у нехтування.

Ось які спільні закономірності виглядають на практиці, і чому деякі з них в часі підтримують краще, ніж інші.

## Підхід віки: швидкий для початку, повільний, щоб померти

GitHub wikis і Confluence за замовчуванням для більшості команд. Вони швидко налаштовані, конфігурація не потрібна, і будь-хто може додавати сторінку.

Проблема в тому, що wikis накопичує сторінки швидше, ніж їх підтримують. Простір Confluence для дворічного проекту зазвичай має сторінки, які є точними, сторінок, на яких застарілі сторінки, і не надійний спосіб визначити, який саме цей. Шукати поверхні все одно. Немає процесу перевірки. Нікому нічого не належить.

GitHub wikis має однакову проблему з доданим обмеженням: вони живуть в окремому репозиторії з вашого коду. Запит на отримання повідомлення, що змінює API, не пропонує будь-кому оновити документацію. Розрив між кодом та документацією розширюється.

Команди, які використовують wikis добре є винятком. Зазвичай вони мають спеціалізований технічний письменник стандарти примусового виконання. Більшість команд немає.

## Шум та подібні інструменти: чудовий для внутрішніх команд, що погано підходить для довголіття

Увага до внутрішньої документації — добірні вказівки, пускові книги, командні процеси, вступні процеси, нотатки про зустріч. Редактор - гнучкий і настійний дозволи, і досить легко, що його використовують нетехнічні учасники.

Для документації до проекту це означає жити разом з кодом, і це не так.

Ваші документи знаходяться в базі даних Notions, а не в репозиторії. Немає відмінностей, жодних переглядів PR і автоматичних розгортань. Якщо Notion змінює свої ціни, застаріє функція або просто зникає, міграція - це ручний експорт і реформаторна робота.

Більш глибоке питання - це видимість. Документи, що живуть у Notion не індексуються поруч з твоєю базою коду. Розробник сідає для імені функції не знайде Notion сторінку, яка пояснює, чому він працює таким чином. Ці дві системи не спілкуються одна з одною.

## README: чесний, але важкий у масштабі

Багато менших проектів - і багато з відкритим вихідним кодом - майже повністю покладаються на README. Один файл, збережений поточний, покриває встановлення, використання та рекомендації з внеском.

Це працює напрочуд добре для цілеспрямованих інструментів зі стабільним API. Обмеження одного файлу має пріоритетні значення. Не існує жодної документації, тому що куди б вона пішла.

Він руйнується, коли проект зростає з певною складністю. README, яка охоплює п'ятнадцять різних варіантів конфігурації, три цілі розгортання, а також міграційний посібник з v1 до v2 припиняє читання. У цей момент команди дали їй пройти або збудувати щось інше.

## Документ як код: візерунок масштабу

Проекти з послідовною документацією, як правило, використовують той же самий основний шаблон: Markdown у репозиторії, побудований статичним генератором сайтів, розгорнутий поруч з кожним випуском.

Документи Kubernetes знаходяться в тому ж монорепі що і кодова, рецензована в тому ж робочому процесі запросів. Rust Book - це проект Markdown на GitHub з сотнями учасників. Документація Astro-це сайт Astro Starlight, який здійснюється поряд з самою структурою.

Але що змушує цю роботу не використовувати інструмент. Це робочий процес. Документи відтворюються поруч із кодом, тому вони оновлюються в той час як код змінюється. ПР, який додає новий прапор, повинен оновити документацію перед злиттям. Процес перевірки виконує цю функцію.

Вторинна вигода - довговічність. Файли Markdown з 2015 року все ще розбірливі та доступні в 2027 році. Переселення не вимагається, власних експортних форматів, ніякої залежності від платформи. Вміст — це просто текстові файли з теки.

## Сертифікація вбиває в якості коду для нетехнічних учасників

Справжня слабкість шляху до Markdown-in-Git у тому, що вважається, що всі зручні з текстовим редактором і pull request. Для багатьох команд, у яких все гаразд. Для команд, які не є технічними учасниками - маркетинг, підтримка продукції - це створює тертя, що призводить до ігнорування або підтримки у паралельній системі.

Ось де вміщається Git-підтримуваний CMS ідентифікатор. Інструменти, такі як LightCMS, розміщені перед репозиторієм і надають застосункам роботу з справжнім редактором під час створення файлів Markdown у репозиторій. Редактор обробляє формат. CMS обробляє коміт. Учасник ніколи не бачить термінал.

Результат такий самий, як docs-as-code - вміст у Markdown, версії в Git, розгорнутий наявним конвеєром — але доступний для людей, які не хочуть використовувати Git напряму.

## Що працює в 2027 році

Шаблон, який залишається простим: Markdown файли у ваш репозиторій, побудований за статичним генератором сайтів, перегляд за запитами на злиття.

Конкретні інструменти навколо цієї схеми мають значення менше, ніж робочий процес. Якщо ваша команда використовує GitHub, світло або сайт Starlight або Docusaurus, віддані тому самому репозиторію, то ви отримаєте все: пошук, версія, належне враження про читання та огляд процесу, який зберігає документи синхронізованими з кодом.

Якщо у вас є нетехнічні учасники, додайте перед собою редактор Git-, щоб вони могли писати, не торкаючись терміналу. Основні налаштування залишаються незмінними. Контент залишається в вашому репозиторії.

Проекти, що мають найкращу документацію, не є найкращими інструментами. Саме вони створили частину документації того ж робочого циклу, що й код.

## Часті питання

### Що таке docs-as-код?

Docs-as-code - це практика написання та підтримання документації, використовуючи ті ж інструменти та робочі процеси що і розробка програмного забезпечення: прості текстові файли (зазвичай Markdown), керування версіями (зазвичай Git), огляд коду та автоматизоване розгортання. Це зберігає документацію близько до коду, який він описує і робить оновлення нормального робочого процесу розробки.

### Чи достатньо Markdown для документації?

Так, для переважної більшості проектів. Markdown обробляє заголовки, блоки коду, таблиці, зображення та посилання. Статичні генератори сайтів, такі як Starlight, Docusaurus та МкDocs додають пошук, навігацію, версію та відповідний досвід читання зверху. Обмеження простого тексту є функцією: його розбірливість у будь-якому редакторі, жадібному, мінливому і тривалому протягом десятиліть.

### Як нетехнічні письменники вносять свій внесок до документації Markdown?

Інструменти підтримуваної Git-итацією, такі як LightCMS, забезпечують необхідний редактор вашого репозиторію, не вимагаючи від розробників безпосередньо використовувати Git. Контент залишається в вашому репозиторії в простому Markdown. Редактор - це лише більш доступний інтерфейс для тих же основних файлів.

### Що таке кращий статичний генератор Сайту для документації?

Залежить від вашого стека. Astro Starlight і Docusaurus - це найбільш повнофункціональні варіанти, з хорошим пошуком з коробки. МкДокументи з Матеріалом доступне для Python проектів. Якщо ви вже в Hugo або G-20 для вашого блогу, вони також можуть впоратися з науками. Генератор має значення, окрім збереження документації у тому ж сховищі, що і ваш код.
