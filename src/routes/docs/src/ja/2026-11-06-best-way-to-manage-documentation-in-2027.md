ドキュメントは、誰もが同意するプロジェクトの一部であり、誰もがどのように扱うかについて全く同意するものではありません。 5つのオープンソースプロジェクトを見てください。5つの異なるセットアップがあります。うまくいく人もいる。無視にほとんどのドリフト。

一般的なパターンは実際に実際にはどのように見えるかを示しますなぜある人は時間の経過とともに他人よりも優れているのかを示します

## ウィキアプローチ：早く始める、遅くて死ぬまで

GitHubのWikiとConfluenceは多くのチームのデフォルトです。簡単に設定でき、設定も不要で、誰でもページを追加できます。

問題は、Wikiがメンテナンスされるよりも早くページを蓄積することです。 2年前のプロジェクトのための合流空間は、通常、正確なページがあります。 どちらがどちらかを判断する信頼できる方法がないページですすべてのサーフェスを等しく検索します。レビュープロセスはありません。誰も所有していません。

GitHub Wikiは追加された制約と同じ問題を抱えています:それらはあなたのコードとは別のリポジトリに住んでいます。 API を変更するプルリクエストは、誰にでもドキュメントの更新を促すことはありません。コードとドキュメントのギャップは静かに広がります。

wikiをよく使うチームは例外です。彼らは通常、専用の技術的なライターの基準を執行しています。ほとんどのチームは違います。

## 概念および類似のツール：内部チームに最適、長寿に悪い

Notionは内部ドキュメントには本当に良いです — オンボーディングガイド、ランブックス、チームプロセス、ミーティングノート。エディタは柔軟で、権限は粒度が高く、技術的でない貢献者が実際にそれを使用するのは簡単です。

コードと共に生きることを意味するプロジェクト文書では、いくつかの点で短くなります。

ドキュメントはリポジトリではなく、Notionのデータベースにあります。差分も、PRレビューも、自動デプロイもありません。 Notionが価格を変更したり、機能を非推奨にしたり、単純に終了したりすると、マイグレーションは手動でのエクスポートとジョブの再フォーマットになります。

より深い問題は発見可能性です Notionに住んでいるドキュメントは、コードベースと一緒にインデックスされません。開発者が関数名をgrepping しても、なぜ機能するのかを説明する notion ページは見つかりません。二つのシステムはお互いに話しかけません

## README駆動：正直だが規模を拡大するのは難しい

多くの小規模なプロジェクトや、多くのオープンソースプロジェクトは、README に完全に依存しています。 1つのファイルは、現在のまま、インストール、使用状況、貢献ガイドラインをカバーしています。

これは、安定したAPIを持つフォーカスされたツールでは驚くほどうまく機能します。 1つのファイルの制約は優先順位付けを強制します。どこにも行けないので文書化はありません。

プロジェクトがある複雑さを越えると壊れてしまいます 15の異なる設定オプション、3つのデプロイターゲット、およびv1からv2への移行ガイドをカバーするREADMEは読めなくなります。その時点で、チームは腐敗させるか、何か他のものを作り始めます。

## Docs-as-code: 拡大縮小パターン

一貫して優れたドキュメントを持つプロジェクトは、リポジトリ内のMarkdownファイルと同じ基本パターンを使用する傾向があります。 静的サイトジェネレータによって構築され、すべてのリリースと共にデプロイされます。

Kubernetesドキュメントは、コードベースと同じmonorepoにあり、同じプルリクエストワークフローでレビューされます。 Rust Book は GitHub 上の Markdown プロジェクトで、何百人ものコントリビューターを抱えています。 Astroのドキュメントは、フレームワーク自体と一緒にコミットアストロスターライトサイトです。

この作品を作るのは工具ではありません。これはワークフローですドキュメントはコードの隣にあるので、コードが変更されたときに更新されます。新しいフラグを追加するPRは、マージする前にドキュメントを更新する必要があります。レビュープロセスはそれを強制します。

二次的な利点は耐久性です。 2015 年の Markdown ファイルは依然として読み取り可能で、2027 年にデプロイ可能です。移行は不要で、独占的なエクスポート形式もなく、プラットフォームの依存性もありません。コンテンツはフォルダ内のテキストファイルにすぎません。

## 非技術的な貢献者のためのコードとしてのドキュメントを殺すフリクション

Markdown-in-Gitアプローチの本当の弱点は、誰もがテキストエディタとプルリクエストに慣れていると仮定していることです。多くのチームにとって、それは問題ありません。テクニカルではない貢献者(マーケティング、製品、サポート)を持つチームでは、並列システムで無視または維持されるドキュメントにつながる摩擦を生じます。

ここでは、GitにバックされたCMSが適合します。 LightCMSのようなツールはリポジトリの前にあり、Markdownファイルをリポジトリにコミットしながら貢献者に実際のエディタ体験を与えます。エディタが書式設定を処理します。 CMSはコミットを処理します。貢献者はターミナルを見ることはありません。

結果は docs-as-code と同じです — git でバージョン管理された Markdown のコンテンツ 既存のパイプラインによってデプロイされますが、Git を直接使用したくないユーザーはアクセスできます。

## 2027年に実際に動作するもの

保持するパターンは簡単です。リポジトリ内のMarkdownファイルは、静的なサイトジェネレータによって構築され、プルリクエストでレビューされ、マージにデプロイされます。

そのパターンの周りの特定のツールは、ワークフローよりも重要ではありません。あなたのチームが GitHub を使用している場合、Starlight または Docusaurus サイトが同じリポジトリにコミットされている場合、すべてのものを提供します: 検索。 バージョン管理、適切な読み取り体験、およびコードと同期を保つレビュープロセス。

技術的な貢献者でない場合は、Gitにバックアップされたエディタをその前に置いて、端末に触れずに書くことができるようにします。基本的なセットアップは同じままです。コンテンツはリポジトリに残ります。

最高のドキュメントを持つプロジェクトは、最高のツールを持つプロジェクトではありません。それらはコードと同じワークフローのドキュメントを作ったものです。

## よくある質問

### docs-as-codeとは

Docs-as-code は、ソフトウェア開発と同じツールとワークフローを使用してドキュメントを作成し、維持する方法です。プレーンテキストファイル(通常はMarkdown) バージョン管理(通常はGit)、コードレビュー、および自動デプロイメント。ドキュメントを記述するコードに近づけ、通常の開発ワークフローの一部を更新します。

### Markdownはドキュメントに十分ですか?

大多数のプロジェクトではそうです Markdownは見出し、コードブロック、表、画像、リンクを処理します。 Starlight、Docusaurus、MkDocsなどの静的サイトジェネレータは、検索、ナビゲーション、バージョン管理、適切な読み取り体験を追加します。プレーンテキストの制約は特長です:何十年にもわたってどのエディタでも可読性、貪欲性、拡散性、耐久性があります。

### テクニカルではない作家はMarkdown文書にどのように貢献するのでしょうか?

LightCMSのようなGit-backgroundCMSツールは、貢献者がGitを直接使用することなく、Markdownをリポジトリにコミットするリッチエディタを提供します。コンテンツはプレーンマークダウンでレポに留まります。エディタは、同じ元のファイルへのよりアクセスしやすいインターフェイスです。

### ドキュメントに最適な静的サイトジェネレータは何ですか?

スタックに依存します。 Astro StarlightとDocusaurusは、箱の中から良い検索を備えた最もフル機能のオプションです。 MkDocs with Material は、Python プロジェクトに最適です。あなたのblog のためのヒューゴかEleventy に既にあれば、彼らは余りにdocs を扱うことができる。ジェネレータは、コードと同じリポジトリにドキュメントを保持するよりも重要です。
